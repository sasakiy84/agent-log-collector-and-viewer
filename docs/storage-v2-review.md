# ストレージ世代2のレビュー記録

v0.23.0からの全面移行を対象に、保存・関連付け、オフライン移行、フロントエンド・取得性能の観点を入れ替えて独立レビューしました。実装とレビューを別担当でも確認し、P1/P2の指摘へ対応しています。

| 優先度 | 指摘・確認項目 | 対応 |
|---|---|---|
| P1 | ACK済み未反映キュー、監視状態、削除抑止情報の欠落 | 主DB以外に受信DB全体とアーカイブファイルを移送。原本・キー・墓標をバイト単位で検証 |
| P1 | 原本JSONの再シリアライズで照合用ハッシュが変わる | BLOBを再JSON化せずコピー |
| P2 | usage_pointsの暗黙rowidを詰めると区間索引が別計測を参照 | 暗黙rowidも移送・digest検証。欠番87/99の独立再現で結合結果を確認 |
| P2 | 正常な旧DBでも退役skills.v1の未完了行が残る | 後継skills.reads.v2が正常完了した場合だけ退役jobを検査対象外にする |
| P2 | contentless FTSから本文を読んで再索引できない | 元のFTS索引を位置情報ごと保持し、FTS整合性と日本語・フレーズ検索を検証 |
| P2 | 初期化で過去修復を待つため新着反映が遅れる | Goから歴史修復コードを除去。移行済みDBでは永続pendingだけを回復 |
| P2 | 値が変わらないUPDATEでもトレース全体を再解決 | 祖先・所属・分類の実差分条件を追加。infoだけ変わるケースもテスト |
| P2 | 詳細のスキル集計でスキル数に比例してSQLを発行 | 集合SQLと代表根拠選択へ変更。origin/plugin/統合IDの意味を維持 |
| P2 | プロジェクト取得が一覧・Skillsの表示をブロック | 描画・失敗を独立化。両方向の失敗と条件復元もブラウザで確認 |
| P2 | 移行と本番でcheckoutが異なる手順 | 移行時のcommitを記録し、本番も同じcommitへ切り替える手順を記載 |
| P3 | 共通work表で旧FKの孤児削除を失う | 原本削除時にrecord/search/skill-read workを除去。削除集計に必要なtimeline workは保持 |
| P3 | 不一致の受信DB履歴が移行後のGo起動で判明する | 旧inbox履歴をPython側でも事前検証 |
| P3 | 強制終了では作業ディレクトリが残り得る | 完成品として公開されないことと残存stageの扱いを文書化 |

## 検証範囲

- 実v0.23.0バイナリで作ったDBをPythonで移行し、新Goで起動。60種類のAPI応答を比較。原本別・統合後の会話、検索、使用量、Skills、子セッション、APIキー、エクスポートが一致。
- Python単独の移行テストは9件。コミット済みWAL、欠番rowid、日本語FTS、R-tree、APIキー、墓標、未反映キュー、watch、採番位置、アーカイブと検証失敗を対象。
- Go通常テスト、関連付け・使用量・スキル・起動・キー管理のrace検証、vet、静的構文チェックを実行。
- 検索条件、会話、プロジェクトの待ち合わせとエラー分離、アーカイブ削除、Settings、Claude/Copilot表示を実ブラウザで検証。PC・モバイルのスクリーンショットを点検。
- Goの通常テストは314件が通過。関連するraceテストも通過。
- Dockerの非root・読み取り専用ルート、永続化、再送重複排除、遅着統合後の原本、3MiB日本語の索引を確認。
- 2k/20k/277k件で初回DOMと遅延取得を測定。同じ200件の表示ではDOM要素数は一定、処理ログ20ページの追記も新しい50件ずつだけ初期化。

合成データの計測（開発環境の参考値）：65万962件で処理ログを最後の会話間へ偏らせたケースは、最新会話APIの初回37.5ms・中央値9.31ms、ブラウザ初回表示312ms。別の27万7,022件ケースは会話API約106ms、応答後の描画約110ms。端末・DB内容によって変動し、本番での速度保証や旧版からの改善率を意味しません。

## 残るP3

- 既存レコードや削除済み原本の再送でも、writer確保前に解析・分かち書きを行う。writer保持時間は短くなるが、大きな再送ではCPUと一時メモリを使う。解析済みキャッシュや楽観的事前判定を入れる場合は、並行更新・墓標・バッチ原子性への影響と比較して判断する。
- フロントエンドにはページ間の共有状態が残る。今回の実害があった待ち合わせ・失敗時の条件混入は修正したが、フレームワーク移行や全面的な画面状態モデルの置換は行っていない。

移行元は完全に準備済みのv0.23.0が対象です。未知の旧形式や未完了の派生状態を推測して補完しません。元DBを保持し、検証済みの別ディレクトリだけを本番へ戻します。十分なCPU・メモリ・ディスクと通信停止は移行作業の前提です。
